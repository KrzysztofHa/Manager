# Test Failures due possible code bugs

## Manager.App.Tests.csproj - LoadListInBase_WhenFileContainsSerializedString_PopulatesList
- **Confidence**: High
- **Test File**: Manager.Tests\Common\BaseOperationServiceTests.cs
- **Bug Location**: Manager.Infrastructure\Common\BaseOperationService.cs@18

### Analysis
The failure is caused by a static initializer in BaseOperationService<T>: the static field PathToFile is initialized via LoadPathToFile() (BaseOperationService.cs line ~18). That method constructs a BasePathsService which (in its constructor) may call LoadListInBase and open the shared BasePaths file. The static initialization runs as soon as the test reads BaseOperationService<TestDto>.PathToFile (or otherwise touches the type), which attempts to open the BasePaths file while some other process (or test) already has it open, producing the IOException. The root cause is production code performing file I/O during type initialization, which is brittle and interferes with tests (and general use). The test is simply exposing this fragility by accessing the static member; the correct fix is to make PathToFile initialization lazy and avoid doing I/O in the type initializer.

### Suggested Fix
Avoid performing file I/O during static type initialization in BaseOperationService<T>. Make PathToFile lazily initialized and allow tests to set it without triggering heavy I/O. One safe approach: replace the static eager initializer with a backing field and a property that lazily resolves the path only when needed. Also keep a public setter so tests can set PathToFile without invoking file I/O. Example change to BaseOperationService.cs:

```csharp
    private static readonly string PathName = typeof(T).Name;
    private static string? _pathToFile;
    public static string PathToFile
    {
        get
        {
            if (string.IsNullOrEmpty(_pathToFile))
            {
                // Lazily resolve the path when actually needed
                var basePathsService = new BasePathsService();
                _pathToFile = basePathsService.GetPathToFileOfTypeName(PathName);
            }
            return _pathToFile!;
        }
        set => _pathToFile = value;
    }
```

Also ensure LoadListInBase and SaveListToBase defensively handle an empty or null PathToFile (return early or throw a clear exception). With this change, simply accessing or assigning BaseOperationService<TestDto>.PathToFile in tests will not trigger immediate file I/O, and tests can set PathToFile to a temp file before constructing instances.

If desired, you can additionally harden BasePathsService to use safer file access (appropriate FileShare, or retry/backoff) but the primary fix is to remove I/O from the static initializer in BaseOperationService<T>.

## Manager.App.Tests.csproj - SaveListToBase_WithValidList_ReturnsTrueAndCreatesFile
- **Confidence**: High
- **Test File**: Manager.Tests\Common\BaseOperationServiceTests.cs
- **Bug Location**: Manager.Infrastructure\Common\BaseOperationService.cs@18

### Analysis
The failure is caused by the static initialization of BaseOperationService<T>. The class declares a static field PathToFile initialized with LoadPathToFile(), which constructs a BasePathsService. That service performs file I/O (LoadListInBase / SaveListToBase) at type initialization time. In the test the code attempts to set BaseOperationService<TestDto>.PathToFile to a temp file, but the CLR runs the type initializer before the assignment, so LoadPathToFile runs first. During that initialization the code attempts to open the shared BasePaths file in the test output directory and an IOException is thrown because the file is locked by another process. Causing a TypeInitializationException in the test. To avoid this fragile behavior the production code should not perform file I/O during type initialization. Instead PathToFile must be initialized lazily (or deferred) so tests can set it and code doesn't run I/O while types are being loaded.

### Suggested Fix
Remove the eager static initialization that calls LoadPathToFile(). Make PathToFile lazily initialized (or a property) so no file I/O happens at type initializer time. Example change (replace the current static declaration and LoadPathToFile usage):

```csharp
// Replace the existing static declaration
// private static readonly string PathName = typeof(T).Name;
// public static string PathToFile = LoadPathToFile();

// With a lazy-backed property
private static readonly string PathName = typeof(T).Name;
private static string _pathToFile;
public static string PathToFile
{
    get
    {
        if (string.IsNullOrEmpty(_pathToFile))
        {
            _pathToFile = LoadPathToFile();
        }
        return _pathToFile;
    }
    set => _pathToFile = value;
}

// And adjust LoadPathToFile so it does not assign to PathToFile (to avoid recursion):
private static string LoadPathToFile()
{
    var basePathsService = new BasePathsService();
    return basePathsService.GetPathToFileOfTypeName(PathName);
}
```

Rationale and additional notes:
- This defers creating BasePathsService and any file I/O until PathToFile is actually requested (e.g. inside instance methods). Tests can set BaseOperationService<T>.PathToFile before creating instances to redirect file access.
- Consider also making LoadListInBase/SaveListToBase robust to file-locking (e.g. catch IOException and surface useful diagnostics) and ensure StreamReader/StreamWriter use appropriate FileShare modes if concurrent readers/writers are expected.
- The primary fix is to avoid side effects in static initialization which may throw and is brittle in test environments.

## Manager.App.Tests.csproj - LoadListInBase_FileContainsJsonNull_SetsListToNull
- **Confidence**: High
- **Test File**: Manager.Tests/Common/BaseOperationServiceTests.cs
- **Bug Location**: Manager.Infrastructure/Common/BaseOperationService.cs:LoadListInBase (around lines 31-36 where jsonOutput is deserialized and passed to JsonConvert.DeserializeObject)

### Analysis
LoadListInBase reads the file into a string via JsonSerializer.Deserialize<string>(jsonReader) and then passes that value (jsonOutput) directly to JsonConvert.DeserializeObject<List<T>>. If the file contains the JSON token null, serializer.Deserialize<string> returns null, and JsonConvert.DeserializeObject<List<T>>(null) will throw an ArgumentNullException. The method neither checks for null nor handles this case, so valid input (a JSON null) causes an exception instead of setting ListOfElements to null as callers/tests expect.

### Suggested Fix
Check jsonOutput for null (or empty) before calling JsonConvert.DeserializeObject. For example: var jsonOutput = serializer.Deserialize<string>(jsonReader); if (jsonOutput == null) { ListOfElements = null; } else { ListOfElements = JsonConvert.DeserializeObject<List<T>>(jsonOutput); } Alternatively, avoid the double-serialization pattern and deserialize directly to List<T> with the JsonSerializer and handle null tokens appropriately.

## Manager.Consol.UnitTests.csproj - GetStringFromUser_BlockingPath_Skipped
- **Confidence**: High
- **Test File**: Manager.Consol.UnitTests\Concrete\ConsoleServiceTests.cs
- **Bug Location**: Manager.Consol\Concrete\ConsoleService.cs@91

### Analysis
The test was marked skipped because ConsoleService.GetStringFromUser and related methods rely directly on Console.ReadKey/Console.KeyAvailable and other mutable static Console state (WindowHeight, WindowWidth, Cursor position, CursorVisible, etc.). These direct static calls make the behavior interactive and environment-dependent and cannot be reliably simulated from a unit test without changing the production code. I inspected the production source (ConsoleService.cs) and confirmed GetStringFromUser immediately calls CheckAndSetSizeWindow (which itself manipulates and polls Console.WindowHeight/WindowWidth and may loop, sleep, or call Environment.Exit) and then enters a ReadKey loop until Enter is pressed. Because these are static Console interactions, the unit test cannot inject keystrokes nor reliably avoid the interactive loops. The root issue is in production code design: ConsoleService is tightly coupled to the static Console API and therefore not unit-testable in these interactive paths.

### Suggested Fix
Refactor ConsoleService to make console interactions injectable so unit tests can simulate key presses and window state. Introduce an abstraction (e.g. IConsole) that exposes the necessary members used by ConsoleService: WindowHeight, WindowWidth, BufferWidth, BufferHeight, CursorLeft, CursorTop, GetCursorPosition(), SetCursorPosition(...), CursorVisible, ForegroundColor, Clear(), ReadKey(bool intercept), KeyAvailable, Write/WriteLine, SetIn/SetOut equivalents if needed, and Thread.Sleep can be wrapped or isolated. Example approach:

1) Define an interface:

```csharp
public interface IConsole
{
    int WindowHeight { get; set; }
    int WindowWidth { get; set; }
    int BufferWidth { get; }
    int BufferHeight { get; }
    int CursorLeft { get; set; }
    int CursorTop { get; set; }
    bool CursorVisible { get; set; }
    ConsoleColor ForegroundColor { get; set; }
    (int Left, int Top) GetCursorPosition();
    void SetCursorPosition(int left, int top);
    void Clear();
    ConsoleKeyInfo ReadKey(bool intercept);
    bool KeyAvailable { get; }
    void Write(string value);
    void WriteLine(string value);
}
```

2) Provide a production implementation that delegates to System.Console, and add a test implementation that allows queued ConsoleKeyInfo values and controllable window/cursor properties.

3) Change ConsoleService to depend on an IConsole instance (either via DI or by passing it into methods). Replace static Console.* calls with calls on the injected IConsole.

4) In unit tests, inject a mock or test-double IConsole (or use Moq) and simulate sequences of ReadKey values and window sizes to exercise both blocking and non-blocking paths deterministically.

By performing this refactor, tests can be written to simulate pressing Enter, Escape, Backspace, etc., and to simulate different window sizes without relying on the real console or causing the test host to block or exit.
